# wevir-sync/1 · Frozen artifact revision 1

These MIT-licensed public artifacts freeze the candidate wire format, not deployment readiness or ZUV's business implementation. The schemas, fixtures, deterministic crypto vectors and state machines are generated by `pnpm --filter @wevir/sync-protocol generate`. Both endpoints must consume this exact artifact revision before interoperability is claimed; client interoperability remains unverified. Changes require a new artifact revision and updated shared fixtures. Host JSON-RPC has its own version.

`SyncOperation` and the encrypted header retain the baseline fields. IDs are opaque, globally unique strings. Decimal strings are canonical unsigned integers, never JSON numbers. `deviceSeq` is unique per device; arrival order is unrestricted. Parents must be unique, observed revisions of the same entity. Deletion may omit payload; all other kinds require one. `resolve` references every current conflict head. Wall clocks never resolve conflicts. Unknown major versions reject writes.

Supplements address information the ciphertext-only gateway cannot infer: commit requests and changes include `recordManifest`, exactly one entry per operation, including deletion without payload. Missing, duplicate and extra entries fail. It binds the payload's blob/record reference, optional stable `projectId`, and, for an origin segment, contiguous `{seq,sha256}` hashes with the domain-separated preimage in `event-hash-vectors.json`. The operation idempotency digest covers its envelope and manifest; the commit digest, raw DPoP body hash and signed receipt also cover manifests. Total origin sequences are bounded at 4096 and request bytes, including manifests, at 1 MiB before expansion. After decryption the client MUST compare the record's opId/entityId/kind/parents, projectId and every event hash with both envelope and manifest before applying or acknowledging. A dishonest sender can supply dishonest metadata; recipients reject a mismatch and retain their local good version. The public decryptor returns only verified referenced records, not unreferenced pack content. The ordinary gateway has no decryption permission. Entity-to-project bindings are immutable after the first committed revision. A project entity's projectId is its entityId; global entities omit projectId. Empty projectIds enables global records only; selected projects require explicit IDs. Categories are always explicit. Imported events keep their original identity and are never re-emitted as a new device's events.

Vault open returns `originHostId`, the server binding for new origin segments from this device (initially the deviceId). Local Host IDs can be mapped to it; a device cannot mint another binding's new events. Origin overlap is validated by (vault, host, session, stream, seq) and the manifest's content hash. The client additionally verifies actual content. Identical independent messages retain distinct origin/op identities.

Credential refresh keeps that binding. A reinstall, recovered old outbox or cloned directory with a new device credential cannot create new events under the old Host. Preserve already committed identities; rebase unsubmitted work into a new device-bound stream and include `recoveredFrom` in its encrypted event content. The corresponding vector fixes that event hash. Never re-upload a mirrored committed event as a newly authored event.

All new device routes use `Authorization: DPoP <access_token>`. DPoP uses the existing Ed25519 JWT with `typ=dpop+jwt`, `alg=EdDSA`, public JWK and `jti,htm,htu,iat,ath`; body-bearing methods require `bht=base64url(SHA256(raw bytes))`. `htu` is the web origin plus path, without query. Every jti is consumed atomically. Exact Content-Length is required; Content-Encoding and Range are rejected. Clients sign and transmit the same bytes. Enrollment poll uses enrollmentId as its DPoP `ath` input and supplies its PKCE verifier. Browser approval uses the existing authenticated session, same-origin CSRF check and recent step-up; no browser cookie becomes a device credential.

All routes are under `/api/wevir`: enrollment/start, enrollment/poll, entitlements; sync/v1/vaults/open, scopes, devices, devices/:deviceId/approve, keys/unlock, blobs/reserve, uploads/:uploadId, commits, commits/:commitId, changes, downloads, downloads/:downloadId, devices/ack, executions/claim|renew|release, vaults/delete; recovery/requests, recovery/requests/:id, recovery/requests/:id/complete, recovery/exports. Existing token/refresh and inference paths retain their versions. `keys/unlock` is routed to the independent key-release process on the same HTTPS origin. Its response is no-store and excluded from body tracing.

Cursors are signed opaque positions in the durable per-vault finalize order, including page position. `changes` never queries S3; notifications are hints only. A restoreId fixes an existing high-watermark and blob allowlist, expires, binds a device, and has independent byte/count quotas. Download tickets are single-use; every retry needs a new reservation. A committed response requires an immutable signed receipt already stored. Pending responses require keeping the client outbox. At-least-once transport does not authorize replaying execution, hooks, installations or approvals.

`entitlements.vault` exposes only the authenticated owner's vault ID, key epoch and state for enrollment/recovery discovery. `GET sync/v1/signing-keys?keyId=...` returns at most one historical receipt public key; an unavailable key fails rather than substituting another. These keys need a trusted deployment/catalog anchor for offline recovery. A stale device acknowledges a completely applied fixed snapshot with `ack.restoreId` and its exact cursor. This clears the reset requirement without enabling sync or authorizing later changes. Never acknowledge merely downloaded bytes.

`wevir-sync-export/1` supports inline ciphertext for small drills or a signed `manifest.json` plus `blobs/<blobId>.bin`. SHA-256 in signed receipts authenticates external bytes. An independently current `wevir-sync-control/1` checkpoint binds head, floor, retired blob digest, key epoch, deletion and revoked devices. An old signed export alone cannot prove deletion/revocation state is current. The public recovery package and CLI require trusted historical public keys and independently supplied RSA recovery keys; private server/DB implementation is not part of this package.

The ciphertext format uses AES-256-GCM, a random per-blob 256-bit DEK, AES-KW under a random 256-bit vault key, 96-bit nonce, 128-bit tag, and the full JCS header as AAD. The pack is compressed once, then encrypted. Archives inside content are data, never recursively extracted. The client enforces 16 MiB decompressed, ratio 64 and bounded nesting during any application-specific extraction. These are recoverable encryption semantics; the operator has a controlled key-release path. This is not a zero-knowledge claim.

No presigned URLs, public object URLs, AWS credentials or tenant-supplied object keys are part of this protocol. No content, filename, local path or secret belongs in errors, receipts, audit or KMS encryption context. All details and pagination are bounded. Expiration does not remove local data and does not turn recovery into continuous synchronization.
