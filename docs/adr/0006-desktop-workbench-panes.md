# ADR-0006：桌面工作台改为窗格模型，界面参考 Codex 与 Claude Code 桌面端

- 状态：Accepted（2026-10-14，维护者在对话中确认设计，决定见 desktop-layout.md §9）
- 日期：2026-10-14
- 任务：R12；影响：R5（子智能体窗格）、R6（设置页的样式）、以后的文件预览、变更、后台任务、计划、终端
- 依据：[桌面工作台布局](../architecture/desktop-layout.md)；[CODEX_RUNTIME_PROMPTS.md](../CODEX_RUNTIME_PROMPTS.md)「界面参考」与 `design-refs/` 01–08（维护者 2026-10-14 给的截图，不进仓库）；T5.2 的三栏布局（[openwork-notes](../research/openwork-notes.md) §9.1，`apps/desktop/src/renderer/src/layout/layout-rules.ts`）

## 背景

- 骨架阶段以 OpenWork 为桌面产品与交互参考（[SKELETON_PLAN](../archive/skeleton/SKELETON_PLAN.md) 的参考仓库表），T5.2 按 openwork-notes §9.1 做了固定的三栏布局：左栏 220–400 可拖；中栏限宽居中、最窄 560；右栏固定 360、默认收起，数据结构是“每会话一组 `{type, …}` 标签”，只放了“概览”，只存在内存里；视口不够时右栏以浮层盖在中栏右侧。这部分没有 ADR，依据是计划与 T5.2 的任务 prompt。
- 维护者 2026-10-14 定：整体界面混合参考 Codex 桌面端与 Claude Code 桌面端；各个窗格都能调尺寸、最大化、关闭，整体布局随打开的窗格种类与数量动态变化（CODEX_RUNTIME_PROMPTS.md「界面参考」；AGENTS.md 已改写）。
- 接下来的界面任务都要一个能放多个窗格的框架：R5 的子智能体列表与详情、置顶摘要卡片；以后的文件预览、变更、后台任务、计划、终端。固定 360 的单个右栏装不下。
- 两家桌面端都不开源，只有截图可以照着做；截图只覆盖窗格区与置顶摘要（desktop-layout.md §0）。

## 决策

1. **界面参考**：桌面端的视觉与交互混合参考 Codex 桌面端与 Claude Code 桌面端，以维护者的截图为准，用 Wevir 自己的设计 token 与组件实现，不拷贝两家的代码与素材。OpenWork 不再是桌面交互的参考；已经移植的 OpenWork 代码（主题模式、Markdown 增量渲染、滚动控制、重连状态机）照旧保留，登记不变。
2. **布局**：工作台由侧栏、主窗格、窗格区组成（desktop-layout.md §1–§2）。主窗格显示 URL 指的东西，只有一个、不能关；窗格区放辅助窗格，每个窗格是一张卡片，装一个或多个标签，每个标签是一种窗格种类的实例。窗格集按会话分（新会话草稿单独一份）。
3. **排布由规则算出来，不做自由停靠**：状态里只有窗格的顺序、焦点顺序与比例；排布函数按窗格数量、种类（最小尺寸、高 / 矮）与窗口尺寸从固定的几个模板里挑（单个、上下、左右、一列高 + 一列上下、网格），放不下就按排列顺序把后面的窗格并成标签（折叠），一个也停靠不下就改浮层（desktop-layout.md §4）。用户能拖分隔条、最大化、关闭、拆分与合并标签，不能把窗格拖到任意位置。
4. **自己实现，不引入布局库**：排布与窗格状态是不依赖 React 的纯函数，分隔条、窗格头等组件自己写（分隔条由现有的 `sidebar-resizer.tsx` 改写），菜单与弹出框用 shadcn CLI 生成的 Base UI 原语（ADR-0004 的做法）。
5. **URL 仍是唯一事实**（T5.2 的约定延续）：URL 决定主窗格显示哪个工作区、哪个会话；窗格区的组成是会话的界面状态，存在本机，不进 URL。只有“可寻址”的窗格内容在主会话路径下加一段（R5 的 `/workspace/:wid/session/:sid/agent/:childId`），布局保证它可见，关掉它就导航回父路由。开关窗格、调尺寸、最大化不产生历史记录。
6. **窗格状态持久化**：右栏标签从“只在本次运行内”改为按会话存在 localStorage（只存 ID、种类、参数与比例，不存内容），最多 200 个会话，会话或工作区从列表消失时清掉（desktop-layout.md §5）。
7. **设置仍是整窗页面** `/settings/:tab`，不进窗格模型。
8. **窗口最小尺寸不变**（960 × 600）。主窗格在窗格区停靠时最窄 440（原来中栏最窄 560）；侧栏能否停靠仍按 560 算，现有行为不变。

## 备选方案

| 方案 | 结论 | 理由 |
|---|---|---|
| 保留三栏，右栏只加标签（只照 Codex） | 不采纳 | 维护者要求窗格都能调尺寸、随数量动态布局；截图 05 的多窗格排布做不出来 |
| 自由停靠的窗格树（VS Code、IDE 式，可把窗格拖到任意边） | 不采纳 | 维护者要的是“随种类与数量自动排布”；自由停靠的状态难以在窗口变窄时合理退化，测试面大；拖动标签留作以后的增强 |
| dockview、FlexLayout、Golden Layout 这类停靠库 | 不采纳 | 都是自由停靠模型，自带一套视觉与 DOM 结构，要大量覆盖样式才能用 Wevir 的 token；排布规则还得在它外面再写一遍；运行时插入 `<style>` 标签的库会被渲染进程的 CSP 拦下（Base UI 的 ScrollArea 遇到过，见 `index.css`），每个都要核对 |
| react-resizable-panels 只做分隔条 | 不采纳 | 它按百分比与组件树管理尺寸，我们的尺寸由排布函数按像素与最小尺寸算出；为一个分隔条引入依赖不值得，现有的侧栏拖动条改一下就够 |
| 窗格组成也进 URL（例如查询参数） | 不采纳 | URL 会很长，“后退”会撤回开关窗格这类小动作；可寻址的内容单独加路径段就够（决策 5） |
| 设置作为主区域里的一个窗格 | 不采纳（维护者 2026-10-14） | 设置是全局的，不属于某个会话；两家桌面端（待截图核对）都是整窗页面 |

## 后果

- T5.2 的 `layout-rules.ts` 只留侧栏的规则，右栏的规则由 `arrange.ts` 取代；`right-panel-tabs.ts`、`right-panel.tsx` 由窗格状态（`pane-state.ts`、`pane-store.ts`）与窗格区组件取代（desktop-layout.md §6.2）。测试覆盖每个模板、断点例子、折叠、尺寸分配、持久化的校验与迁移。
- R5 把“子智能体”登记为一种窗格、给置顶摘要加一节，并加 `agent/:childId` 路由；R6 的设置页沿用 R12 之后的样式；文件预览、变更、后台任务、计划、终端各由以后的任务填内容，R12 只登记种类与占位（只在开发模式里能打开）。
- 本机多了一份按会话的窗格状态（localStorage `wevir.panes.v1`），只有 ID 与比例，与 `last-location.ts` 同一口径，不涉及密钥。
- 风险：没有截图的部分（顶栏左半、左栏、设置页、窄窗口）是按对两家的了解写的，维护者补截图后可能要改；desktop-layout.md §0 与 §9 列出了这些点。
- 窄窗口（960 宽、侧栏停靠）下打开窗格区仍是浮层，与现在一致；侧栏收起后可以并排。

## 补记

1. 2026-10-14，R12：维护者确认设计（desktop-layout.md §9）：设置保持整窗页面；放不下时先折叠、再浮层，不动侧栏；不接管 ⌘W；以后的种类只在开发模式下有占位；尺寸按会话记。新开的东西自成一个窗格、主窗格最小 440、置顶摘要没有内容时按钮不可用且默认开，这三条交给实现方选定。
2. 2026-10-14，R12 第二步：折叠改为按排列顺序决定谁被并（设计稿是按焦点），否则点进被并的窗格会把别的窗格挤进去，布局跟着跳；终端占位先按普通窗格排，放到主窗格下面留给做终端的任务。
